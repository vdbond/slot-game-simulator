# Slot Game Simulator

Java CLI simulator for a 3x3 / 5-payline slot machine. Simulates N rounds against a config-driven reel/paytable model
and reports the realized RTP and standard deviation.

## Requirements

- JDK 25 (configured via Gradle toolchain — Gradle will provision it if it isn't already installed)

## Build, run, test

```bash
./gradlew build   # compile + test
./gradlew test    # unit tests only
./gradlew run     # 10,000,000 rounds with the default config
```

`./gradlew run` is the only supported entry point — there's no fat-jar/`java -jar` packaging. Each run prints the report
to stdout and also writes/overwrites `report-example.txt` in the project root.

### CLI options

| Flag                  | Default            | Meaning                                            |
|-----------------------|--------------------|----------------------------------------------------|
| `--rounds <N>`        | `10000000`         | Number of rounds to simulate                       |
| `--config <resource>` | `game-config.json` | Classpath resource to load reels/paytable/bet from |

Example:

```bash
./gradlew run --args="--rounds 1000000"
```

## Game rules

- 3 reels x 3 rows, 5 fixed paylines, flat bet of 10 credits per round (from config).
- Wins require 3-of-a-kind on a payline; `W1` (wild) substitutes for any symbol except `SCA`.
- `SCA` (scatter) pays on 3+ occurrences anywhere in the 3x3 grid, independent of paylines.
- All winning paylines plus a scatter hit sum additively into one round payout — not "best line only."
- Reel stop mechanic: draw a random index `N` per reel, visible column is `N, N+1, N+2` with wrap-around.

## Design overview

```
com.vdbond
├── domain      Symbol, ReelStrip, Payline/Paylines, Paytable, GameConfig — plain records, no logic
│                beyond trivial accessors/validation
├── config      GameConfigLoader — parses game-config.json (Jackson 3) into GameConfig; a private
│                ConfigDto mirrors the JSON shape so domain types stay Jackson-free
├── engine      SpinGenerator (draws stops from an injected RNG), Grid (resolves stops → visible
│                symbols), WinEvaluator (payline matching + scatter, sums into one round payout)
├── stats       StatisticsAccumulator (running count/total/sum-of-squares, thread-confined,
│                mergeable), SimulationStatistics (derived RTP/variance/SD)
├── simulation  SimulationRunner — spin → evaluate → accumulate loop
└── report      ReportFormatter — renders the final report string
```

**Config-driven, not hardcoded.** Reel strips, the paytable, and the bet all come from
`src/main/resources/game-config.json` — none of those numbers exist in Java source. Paylines and the 3x3 grid size are
the one deliberate exception: they're fixed by game design, not meant to be user-configurable, so they're hardcoded Java
constants (`Paylines.STANDARD`) rather than config entries. Swapping in a different paytable or reel set is a config
change only — the core loop never changes.

## Testing

`./gradlew test` covers:

- **Reel positioning** (`ReelStripTest`) — wrap-around at the end of a strip.
- **Win evaluation** (`WinEvaluatorTest`) — all four worked examples from the math model sheet (non-winning / 15 / 240 /
  220), wild substitution edge cases (`H3 W1 H3`, `W1 W1 W1`, `W1 SCA SCA` not counting as 3 scatters), and additivity
  across multiple winning lines plus a scatter in one round.
- **Config loading** (`GameConfigLoaderTest`), **CLI parsing** (`CliOptionsTest`), **report formatting**
  (`ReportFormatterTest`).
- **Statistics** (`StatisticsAccumulatorTest`) — matches a hand-computed mean/SD on a known sample.
- **End-to-end** (`SimulationRunnerTest`) — 50 repeated 2M-round runs, RTP within ±2% of 93.36% every time.

## Design notes

Parallelism wasn't added — a single-threaded run already finishes 10M rounds in about 3 seconds, so splitting the work
across threads would mostly add complexity (thread-pool lifecycle, merging per-thread accumulators, per-thread RNG
handling) without a meaningful payoff at this scale. If a future version needed it — running at a much larger round
count, for example — the natural fit is
`CompletableFuture`: split the round count across N tasks, give each its own `SimulationRunner` +
`StatisticsAccumulator`, run them with `CompletableFuture.allOf(...)`, and merge the accumulators at the end.
